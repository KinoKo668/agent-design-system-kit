# REG-002：组件搜索与精确解析

- 状态：已实现
- 实现日期：2026-09-01
- 依赖：REG-001、SCH-003、SCH-004、ADR-002、CORE-001
- 适用范围：组件目录发现、页面复用前解析、后续 CLI 与 MCP 查询工具

## 1. 目标

REG-002 让 Agent 能够回答两个不同的问题：

1. **搜索**：当前项目登记了哪些组件和历史版本？
2. **解析**：这个准确逻辑身份是否只有一个可继续处理的 Active 版本，它对应哪份 Contract、哪条 Registry Entry 和哪个 Variant？

搜索可以帮助人和 Agent 发现资产；解析负责安全决策。两者不能混为“猜一个最像的组件”。

## 2. 核心原则

- 只查询已经通过 REG-001 完整性校验的 Snapshot；
- 精确身份为 `projectId + component + assetId`，可选再限定完整版本；
- Resolver 只考虑 `active` Entry；
- 不按 Figma 名称、Node ID、Component Key 或描述猜测身份；
- 不使用拼写纠错、编辑距离、向量相似度或自动降级；
- 零个结果返回 `IDENTITY_NOT_FOUND`；
- 多个结果返回 `IDENTITY_CONFLICT`；
- Superseded 和 Revoked 永远不会被自动用于新页面；
- 不存在适合组件时，后续进入 REG-003 Change Request，不绘制近似组件。

## 3. 搜索合同

```ts
const result = searchComponents(snapshot, {
  projectId: "hatch-demo",
  term: "Button",
});
```

支持的过滤条件：

| 字段           | 规则                                                           |
| -------------- | -------------------------------------------------------------- |
| `projectId`    | 必填，必须是稳定项目 ID                                        |
| `term`         | 可选，仅对 `assetId`、`name`、`profile` 做忽略大小写的完整匹配 |
| `assetId`      | 可选，准确组件 ID                                              |
| `assetVersion` | 可选，完整 SemVer                                              |
| `lifecycle`    | 默认 `active`；显式传 `any` 才查看历史                         |
| `figmaStatus`  | `ready`、`unbuilt` 或默认 `any`                                |

例如 `Button`、`button` 和 `button-v1` 都能准确找到当前 Button；拼错的 `buton` 返回空数组，不会回退到名字相近的资产。

结果按 `assetId` 升序、版本降序、Registry 来源路径升序稳定排序。每项包含：

- 资产身份、版本和内容摘要；
- Contract 名称、Profile、类型和尺寸；
- Approval 引用；
- Lifecycle 与 Figma 状态；
- Contract 和 Registry 的仓库内相对来源路径；
- 本次 `term` 实际匹配的字段。

Search 不返回 Figma Node ID、Component Key 或 File Binding，避免发现接口不必要地扩大物理定位信息范围。

## 4. Availability 不是最终插入许可

搜索结果使用三种派生状态：

| 状态              | 含义                                           |
| ----------------- | ---------------------------------------------- |
| `figma-ready`     | Active Registry Entry 指向 Ready Figma Binding |
| `ensure-required` | Active Entry 尚未建立 Figma Library 资产       |
| `unavailable`     | Superseded 或 Revoked，只能用于历史查看和审计  |

`figma-ready` 只描述 Registry 中记录的 Figma 状态，不表示可以跳过审批和真实节点审计。

当前 Registry 只有 `approvalId`，权威 Approval Record 尚未进入 Snapshot。因此 Resolver 会明确返回 `APPROVAL_GUARD_REQUIRED` 警告；Ready 还会返回 `FIGMA_AUDIT_REQUIRED`。未来 Writer 必须完成这两项检查后才能插入 Instance。

## 5. 精确解析合同

```ts
const result = resolveComponent(snapshot, {
  projectId: "hatch-demo",
  assetId: "button",
  variantSelections: {
    appearance: "secondary",
    state: "disabled",
  },
});
```

Resolver 固定执行：

1. 校验 Query；
2. 用准确项目和资产 ID 查询；
3. 只保留 Active Entry；
4. 可选限制准确 `assetVersion`；
5. 要求结果数量严格等于一；
6. 读取对应 Button Contract；
7. 校验请求的 Variant Property 与 Option；
8. 对未提供的 Variant Property 使用 Contract 默认值；
9. 找到准确的 Variant ID 与稳定 Slot；
10. 返回 Contract、Registry Entry、来源路径与下一动作。

指定旧的 Superseded 版本仍返回 Not Found，不会因为调用方写了版本号就绕过 Lifecycle。

## 6. Variant 解析

Button v1 当前允许：

```text
appearance = primary | secondary
state      = default | disabled
```

空选择解析为 Contract 默认值：

```text
appearance-primary/state-default
```

请求 `appearance = tertiary` 会返回：

```text
/variantSelections/appearance
```

请求不存在的 `tone` Property 会返回：

```text
/variantSelections/tone
```

Resolver 不临时组合一个 Contract 中不存在的 Variant，也不根据 Figma 可见名称猜测稳定 Option ID。

## 7. 两种成功结果

### Figma Ready

```text
status     = figma-ready
nextAction = verify-approval-and-audit-then-insert-instance
```

返回准确 Ready Registry Entry 和 Locator，但同时要求：

1. 验证权威 Approval Record；
2. 打开正确的 Figma File Binding；
3. 回读真实托管标记、Variant 与摘要；
4. 审计通过后才插入 Instance。

### Ensure Required

```text
status     = ensure-required
nextAction = verify-approval-then-ensure-library-asset
```

Unbuilt 是正常的可恢复状态，不冒充错误，也不冒充可插入状态。后续 Writer 应先验证审批，再进入幂等 `ensure`。

## 8. 失败与隐私边界

| 场景                      | 结果                               |
| ------------------------- | ---------------------------------- |
| Query 字段非法            | `VALIDATION_FAILED` + JSON Pointer |
| 没有准确 Active 身份      | `IDENTITY_NOT_FOUND`               |
| 多个 Active 匹配          | `IDENTITY_CONFLICT`                |
| Property 或 Option 未登记 | `VALIDATION_FAILED`                |
| Snapshot 内部关系损坏     | `INTERNAL_ERROR`，要求重新加载     |

冲突错误可以返回 Registry 相对来源路径和匹配数量，但不返回 Node ID、Component Key、File Binding 或其他物理定位信息。

## 9. 公共代码入口

`@agent-design-system-kit/core` 导出：

- `componentSearchQuerySchema`；
- `componentResolveQuerySchema`；
- `searchComponents`；
- `resolveComponent`；
- Search Item、Search Results、Resolution 与 Availability 类型。

正式测试覆盖：准确名称、禁止模糊匹配、Active 默认过滤、历史排序、非法查询、默认 Variant、非默认 Variant、Unbuilt Ensure、旧版本阻断、项目错配、非法 Property／Option 与多 Active 冲突。

## 10. 当前不做

REG-002 不实现：

- 自动创建 Change Request；
- Approval Record Schema 与 Approval Guard；
- MCP 协议 Tool 和 CLI 命令；
- Figma 文件连接、Locator 回读或修复；
- Main Component Ensure 或 Instance 插入；
- 自然语言语义搜索、Embedding 或推荐排序；
- Input、Icon 或其他 Component Profile。

下一步 REG-003 会把 Not Found 转换为正式 Change Request，而不是让 Agent 自行补画。
