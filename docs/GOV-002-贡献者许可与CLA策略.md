# 贡献者许可与 CLA 策略

## 1. 决策

Hatch 当前采用：

- 对外源码使用 PolyForm Noncommercial 1.0.0；
- 商业使用需要另行书面授权；
- 外部贡献者保留其贡献的著作权；
- 在正式 Contributor License Agreement（CLA）发布并被贡献者明确接受之前，不合并外部 PR。

最后一项是 Alpha 阶段的临时失败关闭门禁，不代表拒绝社区讨论。Issue、设计建议、错误报告和 Draft PR 可以正常提交与评审。

## 2. 为什么不能直接采用普通 DCO

[Developer Certificate of Origin 1.1](https://developercertificate.org/) 主要证明提交者有权按项目所示的开源许可证提交内容。Hatch 当前不是 OSI 定义的开源项目，而且项目需要在公开非商业许可之外单独授予商业许可。

仅要求 `Signed-off-by` 无法清楚回答“项目维护者是否可以把第三方贡献包含在商业授权版本中”。因此 DCO 可以在未来作为来源声明使用，但不能替代本项目的 CLA 权利授予。

## 3. 推荐的正式方案

采用 [Harmony Contributor License Agreement](https://www.harmonyagreements.org/agreements) 的思路，而不是 Copyright Assignment：

1. 分别准备个人贡献者与组织贡献者版本；
2. 贡献者保留 Copyright，不要求转让所有权；
3. 向明确的项目法律主体授予永久、全球、非独占、可转让、免版税、不可撤销且可再许可的 Copyright License；
4. 包含与贡献相关的 Patent License；
5. Outbound 选择应允许项目同时按当前公开许可证和单独商业／专有许可证分发贡献，并保证该贡献继续能按提交时的公开项目许可证获得；
6. 文档、图像、Token 样例与其他非软件 Material 必须纳入同样清楚的授权范围；
7. 贡献者声明有权提交内容，并披露雇主或第三方权利限制。

Harmony 的标准模板明确区分 License 与 Assignment，并提供允许公开许可证加商业／专有许可证的 Outbound 选项。正式采用前仍需根据 Hatch 的 Source Available 模式、司法辖区和维护者身份完成专业法律复核；本文不是最终法律协议。

## 4. 启用 CLA 前必须完成的事项

- 确定接收授权的真实个人或法律实体名称与联系地址；
- 由合格法律专业人士确认个人版、组织版和隐私告知；
- 固定 CLA 版本号与不可变文本；
- 选择不依赖自建服务器的电子接受方式；
- 记录 GitHub 身份、CLA 版本、接受时间和组织授权身份；
- 在 PR Check 中只显示通过／未通过，不公开不必要的个人信息；
- 定义机器人、匿名贡献、共同作者、未成年人和雇主所有代码的处理规则；
- 对已接受贡献保留可审计、可导出的接受记录；
- 更新 `CONTRIBUTING.md`，移除临时禁止合并门禁。

## 5. 低运营成本的执行方式

首选 GitHub 原生流程：

```text
贡献者打开 PR
→ Check 判断 GitHub 身份是否接受当前 CLA 版本
→ 未接受时跳转到固定 CLA 文本与电子确认
→ 接受记录写入受保护的独立记录
→ Check 通过后才允许 Merge
```

实现可以使用 GitHub Actions 和受保护的私有记录，不需要运行常驻业务服务器。任何第三方 CLA Service 都必须先审查其维护状态、权限、数据保存位置和退出／导出能力，不能只为方便而授予仓库写权限。

## 6. 当前合并规则

在以上事项全部关闭前：

- 仓库所有者自己的提交可以正常合并；
- 外部 Issue、Review、测试结果和设计建议可以正常使用；
- 外部 PR 可以用于讨论和验证，但不得合并其代码、文档、图片或其他具有独立版权表达的内容；
- 不得让贡献者通过 PR 评论临时粘贴一句授权文字来绕过正式协议；
- 不得把普通 DCO Sign-off 表述成已取得商业再授权权利。

完成条件是：最终 CLA 文本、接收主体、电子接受记录、隐私说明和 Branch Protection Check 均可被公开验证，并通过一次测试账号的端到端演练。
