# ADR-002：稳定身份、版本、幂等与迁移策略

- 状态：已接受
- 决策日期：2026-08-30
- 依赖：DIR-001、DIR-002、ARCH-001、SPIKE-001、SPIKE-002
- 适用范围：Git 设计事实、Component Registry、Writer Command、Operation Result 与 Figma 托管资产

## 1. 决策背景

本项目必须在以下情况中仍能认出“同一个设计资产”：

- Figma 节点被改名或移动到其他 Page；
- MCP Server 或 Figma Plugin 重启；
- 同一命令因超时被重新提交；
- Registry 回写失败，但 Figma 已经完成部分写入；
- Token 或 Component 发布了兼容更新或破坏性新版本；
- 多个 Agent 在不同会话中操作同一个项目。

Figma 的节点名称、Node ID、Component Key、Git 文件路径和聊天上下文都不能单独承担长期逻辑身份。本 ADR 将逻辑身份、内容版本、Figma 物理绑定和一次执行身份分开定义。

## 2. 核心结论

| 问题 | 决定 |
| --- | --- |
| 逻辑身份 | `projectId + assetType + assetId`，一经发布永久保留且不包含版本 |
| 设计资产版本 | 严格 SemVer `MAJOR.MINOR.PATCH`，与 Schema、软件 Release 分开 |
| Schema 版本 | 每个持久化文档和跨进程消息都携带严格 SemVer `schemaVersion` |
| 内容摘要 | RFC 8785 JCS 规范化后计算 SHA-256，格式为 `sha256:<lowercase-hex>` |
| Figma 身份 | Shared Plugin Data 中的结构化托管标记是主身份；Node ID 和 Key 只是定位提示 |
| Figma 版本轨道 | 同一逻辑资产的同一主版本复用一个物理资产；新主版本默认并存 |
| 写入模型 | Library 资产使用 `ensure` 收敛；页面 Instance 使用唯一 `placementId` 插入 |
| 幂等模型 | `idempotencyKey + commandFingerprint`；同键同内容重放，同键异内容冲突 |
| 队列恢复 | FIFO 保持内存态；追加式本地 Operation Log 提供解释和有限期重放证据 |
| 数据迁移 | 显式、逐版本、可预览、可重复；读取和启动不得静默改写正式文件或 Figma |
| 删除策略 | MVP 不自动删除或批量替换；弃用资产保留 Tombstone 和迁移提示 |

## 3. 四种身份必须分开

### 3.1 逻辑资产身份

逻辑身份回答“这在设计系统里是什么”。最小元组为：

```json
{
  "projectId": "kite",
  "assetType": "component",
  "assetId": "button"
}
```

规范显示形式为：

```text
ads://kite/component/button
```

规则如下：

- `projectId`、`assetType` 和 `assetId` 使用小写 ASCII；
- `projectId` 和 `assetType` 是单个 kebab-case 片段；
- `assetId` 可以由 `/` 分隔的多个 kebab-case 片段组成；
- 单个片段匹配 `^[a-z][a-z0-9-]*$`；
- ID 表达语义，不使用数组下标、时间戳、随机 UUID、Figma Node ID 或文件路径；
- ID 不包含版本、审批状态、可见名称或所在 Page；
- 已进入评审或发布的 ID 不得改给另一个概念使用。

例如 `button` 改名为界面上的 “Action Button”，逻辑 ID 仍为 `button`。如果语义确实被拆分为新组件，应创建新 ID、保留旧 ID 的 Tombstone，并提供迁移关系，不能直接重命名历史身份。

### 3.2 内容版本身份

内容版本回答“这个资产的哪一版规则”。它由逻辑身份加 `assetVersion` 组成：

```text
ads://kite/component/button@1.2.0
```

版本不改变逻辑身份。审批记录必须继续绑定准确的逻辑身份、版本和内容摘要。

### 3.3 Figma 物理绑定身份

Figma 物理绑定回答“哪个 Figma 对象承载这一条资产版本线”。它至少包含：

```json
{
  "projectId": "kite",
  "assetType": "component",
  "assetId": "button",
  "channel": "library",
  "majorVersion": 1,
  "role": "component-set",
  "slotId": "root"
}
```

物理绑定的唯一元组还包括 `role + slotId`。一个逻辑组件需要多个 Figma 节点时，根节点使用 `slotId: root`，Variant 等子资产使用 Contract 中确定性的 Slot，例如 `variant/appearance-primary/state-default`，不能使用子节点顺序。

同一逻辑资产可以有多个物理绑定：Review 与 Library 分开，不同 Major 版本也分开。`button@1.x` 的兼容更新继续收敛到 Major 1 的 Component Set；`button@2.0.0` 默认创建 Major 2 的新 Component Set，Major 1 保留给已有 Instance。

### 3.4 操作与放置身份

执行身份回答“这是不是同一次请求”：

- `operationId`：一次被接受的执行记录 ID，使用 UUID；
- `idempotencyKey`：调用方在重试期间保持不变的幂等键；
- `placementId`：一个页面 Instance 的业务身份，使用 UUID，由调用方在首次请求时生成并在重试时复用。

`operationId`、`idempotencyKey` 和 `placementId` 都不能代替 Component 或 Token 的逻辑身份。

## 4. 稳定 ID 的生命周期

### 创建

- 新 ID 在 Schema 校验通过后进入 `draft`；
- 首次提交人工评审后，该 ID 被永久占用；
- 不同 `assetType` 可以使用相同 `assetId`，但完整逻辑元组必须唯一。

### 修改

- 可见名称、描述、Page 位置和 Git 文件位置可以变化；
- 语义不变时不得因为整理目录而创建新 ID；
- 已提交评审的准确版本内容不可原地修改，变更必须创建新版本。

### 弃用与删除

- 已发布 ID 不得被回收复用；
- Registry 用 Tombstone 保存最后版本、替代项、原因和日期；
- `superseded` 或 `revoked` 资产不得用于新插入，但已有 Instance 不自动删除；
- MVP 不提供永久删除已发布 Figma 资产的自动命令。

## 5. 三类版本互不混用

| 版本 | 示例 | 表达内容 |
| --- | --- | --- |
| `schemaVersion` | `1.1.0` | JSON 或跨进程消息结构 |
| `assetVersion` | `2.0.0` | Brief、Direction、Token、Contract 等设计事实 |
| Toolkit Release | `0.1.0` | 本项目软件发布版本 |

升级 Toolkit 不会自动升级设计资产；修改 Token 也不会自动修改 Schema 版本。

本项目采用 [Semantic Versioning 2.0.0](https://semver.org/) 的三段格式。持久化正式记录禁止省略 Patch 位，因此使用 `1.0.0`，不使用 `1.0`。

## 6. 设计资产版本规则

### 通用规则

- `PATCH`：不破坏现有引用和公开行为的修正；
- `MINOR`：向后兼容地增加能力；
- `MAJOR`：现有消费者需要迁移的变化；
- 已提交 `in_review` 的版本内容冻结；修改后必须产生新版本；
- 已批准版本不可覆盖；后续批准通过 `supersedes` 指向前一版本；
- 降级不是普通更新，必须使用显式 Rollback 或 Migration Plan。

### Token Set

| 变化 | 版本级别 |
| --- | --- |
| 只修改说明或不影响解析的元数据 | Patch |
| 调整现有 Token 值，但不改变类型和语义 | Patch，仍需重新审批并审计视觉影响 |
| 新增 Token、Mode 或向后兼容 Alias | Minor |
| 删除或重命名 Token、改变类型、改变既有语义 | Major |

### Component Contract

| 变化 | 版本级别 |
| --- | --- |
| 现有 Contract 内的兼容视觉修正 | Patch |
| 新增可选属性、Variant 或不改变原默认值的能力 | Minor |
| 删除或重命名属性／Variant、改变默认语义、要求页面迁移 | Major |

### Brief 与 Direction

- 文案修正但产品与视觉意图不变：Patch；
- 增加向后兼容的场景或指导：Minor；
- 目标用户、品牌方向或关键限制发生改变：Major。

版本级别是最低要求。设计负责人或技术负责人可以因为风险提高版本级别，但不能降低已判定的破坏性变更。

## 7. Schema 版本兼容规则

所有 Git 持久化文档、Writer Command、Operation Result、Figma 托管标记和 Migration Plan 都必须携带 `schemaVersion`。

读取规则：

1. 已明确支持的准确版本：允许读写；
2. 同一 Major 的旧版本：允许通过已登记迁移链读取，正式写回前必须显式迁移；
3. 同一 Major 的未知更新 Minor：最多只读，并返回警告；不得由旧 Writer 写回；
4. 未知 Major：返回 `SCHEMA_VERSION_UNSUPPORTED`；
5. 缺少版本：仅允许显式 Legacy Import，不允许猜测后进入正式写入。

Schema 的 Patch 用于不改变结构语义的修正，Minor 只能做向后兼容扩展，Major 表示需要迁移的破坏性变化。

## 8. 内容摘要

### 算法

1. 解析文件并通过对应 `schemaVersion` 校验；
2. 生成该文档类型的“可审批内容投影”；
3. 使用 [RFC 8785 JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785.html) 规范化；
4. 对 UTF-8 字节计算 SHA-256；
5. 输出小写十六进制：`sha256:<64-hex>`。

不能用原文件字节直接计算，因为空格、缩进和对象键顺序不应该让批准失效。

### 包含内容

- `schemaVersion`、逻辑身份和 `assetVersion`；
- 所有由作者控制且会影响语义、视觉、交互、使用规则或无障碍的字段；
- 数组顺序默认有意义，只有 Schema 明确声明为集合时才允许排序；
- 上游依赖的身份和版本引用。

### 排除内容

- `contentDigest` 自身；
- 审批决定、派生状态和校验输出；
- `createdAt`、`updatedAt`、`generatedAt` 等运行时间；
- Git commit、Figma Node ID、Component Key 等外部定位信息；
- Operation、日志和本地缓存字段。

每个文档 Schema 必须实现明确的 `toDigestSubject`，不得在通用 Hash 函数中凭字段名随意删除内容。

同一完整逻辑身份与版本出现不同摘要时必须返回 `CONTENT_DIGEST_CONFLICT`，不得覆盖原版本或继续使用旧审批。

## 9. Figma 文件绑定

首次把项目连接到 Figma 文件时，Writer 在 `DocumentNode` 的 Shared Plugin Data 中写入：

```json
{
  "schemaVersion": "1.0.0",
  "projectId": "kite",
  "fileBindingId": "<uuid>",
  "fileRole": "design-system-library"
}
```

规则如下：

- 正式命令必须声明期望的 `projectId` 和 `fileBindingId`；
- 未绑定文件只允许执行显式 `bind_file`；
- 不匹配时返回 `FILE_BINDING_MISMATCH`，不得自动改绑；
- 重新绑定、接管复制文件或更换项目必须经过显式命令和人工确认；
- `figma.fileKey` 可用时登记为定位信息，不可用时不作为阻塞条件；
- Figma 文件名不是身份，Session Token 也不得写入文件。

复制 Figma 文件会复制 Shared Plugin Data。在无法读取 `figma.fileKey` 的插件环境中，系统不能自动证明两个完全相同的副本是不同文件，因此复制后的第一次正式使用必须由用户执行 `rebind_file`。这是 MVP 的已知平台限制，不得用文件名猜测绕过。

## 10. Figma 托管标记

正式 Writer 使用固定 Shared Plugin Data：

```text
namespace = agent_design_system_kit
key       = managed-asset
```

值为结构化 JSON。身份字段始终存在；`assetVersion` 和 `appliedDigest` 只在审计成功后写入。完整状态示例为：

```json
{
  "schemaVersion": "1.0.0",
  "projectId": "kite",
  "assetType": "component",
  "assetId": "button",
  "channel": "library",
  "majorVersion": 1,
  "role": "component-set",
  "slotId": "root",
  "phase": "applied",
  "assetVersion": "1.2.0",
  "appliedDigest": "sha256:<digest>"
}
```

选择 Shared Plugin Data 而不是私有 Plugin Data，是因为私有数据会随 Plugin ID 变化而不可读。Figma 官方说明 Shared Plugin Data 可被其他插件读取，因此标记中只能放身份和校验信息，不能放 Session Token、凭据或隐私内容。每条记录必须远小于 Figma 的 100 kB 上限，参见 [Figma Shared Plugin Data](https://developers.figma.com/docs/plugins/api/properties/nodes-setsharedplugindata/)。

`appliedDigest` 表示 Writer 最后一次通过审计的期望内容，不是“当前节点绝对没有被人工修改”的证明。Audit Engine 必须读取真实属性重新校验，不能只信任标记。

创建骨架后、完整审计前，标记使用 `phase: "creating"`，并记录 `pendingOperationId`、目标版本和目标摘要；此时不得出现 `appliedDigest`。恢复流程据此继续收敛，而不能把半成品当成已发布资产。

## 11. Figma 定位顺序

Registry 可以保存以下定位信息：

- `fileBindingId`：必须；
- `nodeId` 或 Variable ID：文件内快速定位提示；
- `componentKey`、`componentSetKey` 或 Variable Key：发布后跨文件导入提示；
- Figma 文件或评审 URL：人工证据。

解析顺序固定为：

1. 验证 Document 的 `projectId + fileBindingId`；
2. 使用 Registry Locator 快速读取候选对象；
3. 校验候选对象的完整托管标记；
4. Locator 失效时，在允许范围内按托管标记重新扫描；
5. 扫描结果为一个时修复 Registry Locator；
6. 为零时返回 `IDENTITY_NOT_FOUND`；超过一个时返回 `IDENTITY_CONFLICT`。

Node ID 在当前文档中可用于 `getNodeByIdAsync`，而已发布 Component 的 Key 可用于 Library Import，但它们都只是平台定位符。相关能力参见 Figma 的 [Node ID](https://developers.figma.com/docs/plugins/api/properties/nodes-id/) 与 [ComponentNode](https://developers.figma.com/docs/plugins/api/ComponentNode/) 文档。

正式资产不得只按名称自动接管。Legacy 资产必须通过显式 `adopt_asset` 命令，指定准确 Node ID、预期逻辑身份、Dry Run 结果和人工确认；出现多个名称匹配时始终阻断。

## 12. 两种不同的写入语义

### Library `ensure`

Token、Variable、Main Component、Component Set 和托管说明节点使用 Ensure 语义：

```text
ensure(project, logical identity, major track, desired version, digest)
```

相同输入重复执行必须收敛到同一物理资产，不创建副本。

### Page `insert_instance`

用户每次明确要求在页面中新增一个组件时，业务上允许创建新 Instance。请求必须携带新的 `placementId`：

```text
insert_instance(component identity, variant, placementId, properties)
```

- 同一 `placementId` 重试：定位并返回原 Instance；
- 新 `placementId`：创建新的 Instance；
- `placementId` 写入 Instance 托管标记；
- 不允许仅根据 Label、坐标或页面名称判断是否为重复 Instance。

这保证“重复运行建库不重复”和“用户确实需要两个按钮”不会被错误地当成同一个问题。

## 13. Writer 的幂等执行算法

每个正式写入按以下顺序执行：

1. 校验 `schemaVersion`、项目、目标、版本、摘要和 Approval；
2. 对命令的语义内容计算 `commandFingerprint`；
3. 检查 `idempotencyKey` 是否已经绑定 Fingerprint；
4. 验证 Figma 文件绑定；
5. 按完整托管标记解析目标，名称只用于显示；
6. 零个目标时创建骨架，并立即写入不含成功摘要的身份标记；
7. 一个目标时逐字段收敛；多个目标时停止；
8. 执行真实属性、Token 绑定、Variant 和来源审计；
9. 审计通过后最后写入 `assetVersion + appliedDigest`；
10. 原子更新 Registry Locator；成功后再把 Operation 标记为完整成功并返回结果。

状态比较规则：

| Figma 实际标记 | 目标 | 行为 |
| --- | --- | --- |
| 同版本、同摘要且真实审计通过 | 相同 | `unchanged` |
| 同版本、不同摘要 | 冲突 | `CONTENT_DIGEST_CONFLICT` |
| 同 Major、目标版本更高 | 兼容更新 | 按迁移计划或普通 Ensure 收敛 |
| Figma 版本高于目标 | 请求过期 | `VERSION_CONFLICT` |
| 目标 Major 更高 | 破坏性更新 | 默认新建 Major 轨道，旧轨道保留 |
| 目标版本更低 | 降级 | `DOWNGRADE_BLOCKED` |

Figma 没有跨节点事务。发生部分写入时不得假装完整成功，也不得盲目删除刚创建的对象；返回 `PARTIAL_WRITE`，保留稳定标记，让同一命令可以继续收敛或进入人工恢复。

Figma 已成功但 Registry 更新失败时同样属于 `PARTIAL_WRITE`。后续重试必须先按托管标记重新定位并补写 Registry，不能重新创建资产。

## 14. 幂等键与命令指纹

`commandFingerprint` 使用与内容摘要相同的 JCS + SHA-256 算法，包含：

- 命令 Schema 版本；
- `projectId` 和 Figma 文件绑定；
- 命令类型；
- 目标逻辑身份、目标版本与内容摘要；
- Approval Reference；
- 经过 Schema 校验的 Payload；
- `placementId`（如果是插入操作）。

它排除：

- `operationId`、`idempotencyKey`；
- 调用客户端名称和显示文案；
- Session Token；
- 提交、派发和完成时间。

行为规则：

- 同一幂等键、同一 Fingerprint：返回原 Operation，必要时继续恢复；
- 同一幂等键、不同 Fingerprint：`IDEMPOTENCY_CONFLICT`；
- 同一 Operation ID 被其他命令占用：`OPERATION_ID_CONFLICT`；
- Asset Ensure 推荐由目标身份、版本和摘要确定性地产生幂等键；
- Instance Insert 的幂等键必须包含调用方新建的 `placementId`。

## 15. Operation Log 与崩溃恢复

MVP 不增加数据库。MCP Server 在本地保存追加式 NDJSON：

```text
.agent-design-system-kit/
└── runtime/
    └── operations/
        └── YYYY-MM-DD.ndjson
```

该目录必须加入 Gitignore，不能进入 GitHub。每条事件至少记录：

- `schemaVersion`、`operationId`、`idempotencyKeyHash`；
- `commandFingerprint`、目标逻辑身份和命令类型；
- `queued`、`dispatched`、`succeeded`、`failed`、`partial` 或 `interrupted`；
- 尝试次数、时间和经过脱敏的 Operation Result；
- 恢复建议。

禁止记录 Session Token、Authorization Header、未脱敏的个人路径或未明确允许公开的 Figma URL。

`idempotencyKey` 是调用方持有的非秘密、不透明字符串；日志只保存它的 SHA-256 摘要。服务用摘要重建索引，避免把调用方原始值长期写入磁盘。

恢复规则：

- 进程启动时重建最近 30 天的幂等索引；
- `succeeded` 或确定失败的相同请求直接重放原结果；
- 上次仍为 `queued` 或 `dispatched` 的记录标记为 `interrupted`，不得静默自动执行；
- 调用方用相同幂等键重试后，系统读取 Git、Figma 标记和真实属性继续收敛；
- 30 天是 Operation Result 的最低本地保留窗口，不是设计资产身份的寿命；
- 即使日志已过期，Figma 的稳定身份和 `placementId` 仍必须阻止资产或 Instance 重复创建。

日志是执行证据，不是新的设计事实源。Git 与 Figma 实际状态始终优先。

## 16. Schema 数据迁移

Schema 迁移必须满足：

- 每一步只处理一个明确的 `fromVersion → toVersion`；
- 函数是确定性的，重复执行得到相同结果；
- 不访问网络，不读取聊天上下文，不修改 Figma；
- 每个迁移有 Before、After、重复运行和失败 Fixture；
- 默认先执行 Dry Run，输出文件差异、版本变化和阻断项；
- 正式执行使用临时文件加原子替换，失败不留下半个 JSON；
- 不跳过未知中间版本；没有完整迁移链时返回 `MIGRATION_PATH_NOT_FOUND`；
- 迁移改变可审批内容时必须计算新摘要并重新审批。

启动、查询和普通校验可以在内存中读取兼容旧格式，但不得借机静默改写仓库。持久化迁移只能由显式 `migrate` 命令或同等人工确认操作触发。

## 17. Figma 资产迁移

Figma Migration Plan 必须声明：

```json
{
  "schemaVersion": "1.0.0",
  "migrationId": "migration.component.button.1-to-2",
  "asset": {
    "projectId": "kite",
    "assetType": "component",
    "assetId": "button"
  },
  "fromVersion": "1.4.0",
  "toVersion": "2.0.0",
  "strategy": "side_by_side",
  "approvalId": "<approval-id>"
}
```

可用策略：

- `in_place`：同 Major 的兼容更新；
- `side_by_side`：新 Major 默认策略，保留旧 Main Component 和已有 Instance；
- `manual`：无法安全自动化的结构或视觉变更。

所有策略都先 Dry Run，列出受影响 Token、Component、Variant 和现有 Instance。完成后必须重新审计并更新 Registry；Registry 切换到新版本前，不得将操作报告为完整成功。

MVP 禁止：

- 自动删除旧 Component 或 Variable；
- 自动批量替换页面中的 Instance；
- 在没有迁移计划和批准记录时执行 Major 更新；
- 通过改名伪装迁移完成。

## 18. Registry 的最小身份字段

后续 SCH-004 至少实现以下语义：

```json
{
  "schemaVersion": "1.0.0",
  "projectId": "kite",
  "asset": {
    "type": "component",
    "id": "button",
    "version": "1.2.0",
    "contentDigest": "sha256:<digest>"
  },
  "approvalId": "approval.component.button.1.2.0",
  "lifecycle": "active",
  "figma": {
    "fileBindingId": "<uuid>",
    "channel": "library",
    "majorVersion": 1,
    "nodeId": "<locator>",
    "componentSetKey": "<optional-published-key>"
  },
  "supersedes": "1.1.0",
  "replacedBy": null
}
```

Registry 中的 Locator 可以修复，逻辑身份、历史版本和审批关系不能因为 Figma 节点移动而改变。

## 19. 标准错误代码

| 错误代码 | 含义 | 恢复动作 |
| --- | --- | --- |
| `INVALID_STABLE_ID` | 逻辑 ID 不符合格式 | 修正 ID 后重新校验 |
| `IDENTITY_NOT_FOUND` | 找不到托管资产 | 确认 Registry，或进入正式创建／接管流程 |
| `IDENTITY_CONFLICT` | 同一物理绑定出现多个对象 | 停止写入并人工清理冲突 |
| `FILE_BINDING_MISMATCH` | 当前 Figma 文件不属于目标项目 | 打开正确文件或显式重新绑定 |
| `UNMANAGED_ASSET` | 只有名称匹配但没有托管身份 | 使用 `adopt_asset` Dry Run |
| `CONTENT_DIGEST_CONFLICT` | 同版本内容不一致 | 创建新版本并重新审批 |
| `VERSION_CONFLICT` | 实际版本与请求版本不兼容 | 刷新 Registry 和请求 |
| `DOWNGRADE_BLOCKED` | 普通命令尝试覆盖为旧版本 | 创建 Rollback Plan |
| `SCHEMA_VERSION_UNSUPPORTED` | 读取器不支持该 Schema | 升级 Toolkit 或运行迁移 |
| `MIGRATION_REQUIRED` | 当前变化需要显式迁移 | 创建并批准 Migration Plan |
| `MIGRATION_PATH_NOT_FOUND` | 缺少连续迁移链 | 补充迁移实现和 Fixture |
| `IDEMPOTENCY_CONFLICT` | 同一幂等键绑定不同命令 | 使用原命令或新幂等键 |
| `OPERATION_ID_CONFLICT` | Operation ID 已被占用 | 读取原 Operation 或生成新 ID |
| `PARTIAL_WRITE` | Figma 只完成部分写入 | 用原幂等键恢复或人工处理 |

错误结果必须包含目标身份、期望与实际版本、已完成步骤以及下一步建议。

## 20. 明确不做

ADR-002 不引入：

- 云数据库或远程队列；
- 分布式锁或多 Writer；
- 自动解决重复稳定 ID；
- 无审批的双向 Figma → Git 覆盖；
- 自动永久删除、自动降级或自动批量迁移页面；
- 把 Shared Plugin Data 当作安全存储；
- 把运行日志提交到 GitHub。
