# DOC-002：故障排查手册

> 适用于当前本地优先 Alpha。本手册只建议可验证、可恢复的动作；不通过伪造 Approval、删除 Marker、修改 Operation Log 或自动重绑 Figma 文件“解决”问题。

## 1. 先做什么

看到失败时，先保留返回结果中的：

- `error.code`：稳定错误码；
- `error.recovery.instruction`：针对当前对象的具体下一步；
- `error.recovery.retry`：什么条件下才能重试；
- `operationId` 和请求中的 `requestId`：原操作的恢复身份；
- 失败前完成的步骤和审计 Finding。

不要依据英文 `message` 做程序判断，也不要为了重试随意更换 UUID。先按 `retry` 分流：

| `retry`                       | 正确处理                                                 |
| ----------------------------- | -------------------------------------------------------- |
| `retry_same_request`          | 先查真实状态，然后保持原 `requestId`／Operation 身份恢复 |
| `retry_after_correction`      | 修正 Catalog、版本、身份或配置后再提交                   |
| `retry_after_external_change` | 等待人工审批、Plugin 重连或凭据轮换等外部状态变化        |
| `do_not_retry`                | 停止原流程，按恢复指令建立新版本、迁移或上报 Bug         |

## 2. 最短健康检查

在仓库根目录运行：

```bash
node --version
pnpm --version
pnpm --silent hatchkit validate \
  --project hatch-demo \
  --root design-system/hatch-demo \
  --brief briefs/hatch-demo.brief.json \
  --token-set tokens/button-foundation.tokens.json \
  --component components/button.component.json \
  --registry registry/components.registry.json
pnpm check
```

预期 Node 为 `v24.20.0`（兼容 `>=22.22 <27`）、pnpm 为 `11.24.0`，Catalog 返回 `status: valid`，统一门禁全部通过。安装起点见 [DOC-001](DOC-001-安装与五分钟Quickstart.md)。

## 3. 按症状定位

### 3.1 安装、构建或门禁失败

1. 确认位于仓库根目录，且 `node --version` 符合范围；
2. 使用 `corepack enable pnpm`，不要用 npm 重写 Lockfile；
3. 执行 `pnpm install --frozen-lockfile`；
4. 用失败门禁对应的单项命令定位：`pnpm format:check`、`pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build`；
5. 不要手工编辑 `dist/`；它是构建产物且被 Git 忽略。

### 3.2 Agent 看不到 Hatchkit Tools

1. 先执行 `pnpm build`，确认 `packages/mcp-server/dist/bin.js` 存在；
2. 确认 Host 工作目录是仓库根目录，否则将 MCP 脚本和 Catalog Root 改为绝对路径；
3. 重启 Agent Host，先调用 `hatchkit_status`；
4. 运行 `pnpm mcp:smoke` 区分 MCP 本身故障与 Host 配置故障；
5. MCP 使用 stdio，stdout 只能输出协议消息，不要在启动脚本中添加调试输出。

### 3.3 只读 Tool 正常，但 Writer／Audit Tool 不存在

这通常是正常的安全默认值。MCP 只在同时获得下列两个进程环境变量时注册 Writer 与依赖 Figma 的 Audit Tools：

```text
HATCHKIT_FIGMA_BRIDGE_URL=http://127.0.0.1:38451
HATCHKIT_FIGMA_BRIDGE_TOKEN=<当前 Bridge 会话 Token>
```

两者缺一会导致 MCP 启动校验失败。Token 不得放入 Git 中的 `.codex/config.toml`、Shell History、Issue 或截图。

### 3.4 Plugin 无法连接 Bridge

1. 确认 Bridge 正在运行，且端口 `38451` 没有被其他进程占用；
2. Plugin 内部连接 `http://localhost:38451`，MCP Writer 必须使用 `http://127.0.0.1:38451`；
3. 仅粘贴本次 Bridge 启动时显示的 Token；旧 Token、断开后 Token 或默认八小时后的 Token 均不可用；
4. 同一 Bridge 只允许一个 Plugin Writer，关闭其他 Figma 文件中的 Hatchkit Writer；
5. 运行 `pnpm figma:bridge-smoke` 和 `pnpm figma:smoke`。

### 3.5 Connected，但写入被拒绝

“Connected”只表示本地通信成功，不表示写入获批。

- `pnpm hatchkit:figma-bridge` 是诊断模式，会主动拒绝全部写入；
- 写入模式必须使用 `--project` 和 `--root` 启动 Bridge；
- Bridge 每次写入前都会重读 Git Approval Record；
- 公开 `hatch-demo` 没有可信人工 Approval，不应伪造记录来绕过门禁。

### 3.6 `FILE_BINDING_MISMATCH`

先确认当前 Figma 文件是否就是 Registry 登记的文件。File Binding 会持久写入 Shared Plugin Data，当前版本没有自动 Rebind：

- 未绑定的独立测试文件：由操作者明确确认后使用 Plugin 绑定；
- 已绑到其他 Project／UUID：停止，不要覆盖；建立单独的 Rebind 评审流程；
- 复制来的文件：把它当作已携带绑定的文件，不要假设复制会清空身份。

### 3.7 超时、断线或进程重启

- `OPERATION_TIMEOUT`：不能假设写入成功或失败；先查 Operation 状态与 Figma 实际状态，再用原请求身份重试；
- `TRANSPORT_UNAVAILABLE`：恢复 Bridge／Plugin 连接后再提交；
- 重启时，上次 `queued`／`dispatched` 会转为 `interrupted`，不会静默续写；
- 只有调用方明确重交原请求才进入恢复。

### 3.8 `PARTIAL_WRITE`

Figma 没有跨节点事务。部分写入时：

1. 保留 `creating` Marker 和 `completedSteps`；
2. 不删除、Detach、Swap 或手工改名半成品；
3. 使用相同 `requestId`、Operation 意图和幂等身份继续收敛；
4. 恢复后重新运行对应审计；
5. Figma 已成功而 Registry 最终化失败时，先重定位原资产并补写 Registry，不得再创建一份。

### 3.9 幂等或身份冲突

- `IDEMPOTENCY_CONFLICT`：同一幂等键被用于不同意图。要么恢复原意图，要么为新意图使用新键；
- `OPERATION_ID_CONFLICT`：同一 Operation ID 对应不同命令。停止并检查调用方；
- `IDENTITY_CONFLICT`：同一稳定身份有多个候选或 Marker 冲突。不能让 Agent 猜一个；
- `UNMANAGED_ASSET`：发现同名但未托管的资产。只能进入显式 Adoption，不按名称接管。

### 3.10 审计返回 Findings

Audit Finding 不是 Core Error Code，它表示读取已成功，但发现不一致：

- 样式：`HARD_CODED_STYLE`、`UNREGISTERED_VARIABLE`，见 [AUD-001](AUD-001-硬编码样式与未登记Variable审计.md)；
- 组件：`DETACHED_OR_APPROXIMATE_COMPONENT`、`UNREGISTERED_COMPONENT_SOURCE`、`UNREGISTERED_VARIANT`、`VARIANT_PROPERTY_MISMATCH`、`INSTANCE_PROVENANCE_MISMATCH`，见 [AUD-002](AUD-002-Instance-Variant与组件来源审计.md)；
- Registry 漂移：`REGISTRY_ASSET_MISSING_IN_FIGMA`、`FIGMA_ASSET_MISSING_IN_REGISTRY`、`FIGMA_ASSET_DUPLICATE`、`FIGMA_MARKER_INVALID`、`FIGMA_ASSET_VERSION_MISMATCH`、`FIGMA_ASSET_DIGEST_MISMATCH`、`FIGMA_LOCATOR_MISMATCH`、`FIGMA_CHILD_SET_MISMATCH`，见 [AUD-003](AUD-003-Registry与Figma双向差异审计.md)。

审计引擎只读，不会自动修复。Figma 或 Git 变化后必须用新 `requestId` 获取新快照。

## 5. Operation Log 怎么用

Bridge 默认将按天追加的 NDJSON 写入：

```text
.agent-design-system-kit/runtime/operations/
```

它被 Git 忽略，保留 30 天幂等和恢复证据。日志只供读取和排查：

- 不要手工增删改文件来改变 Operation 状态；
- 不要把整份日志直接发到 Issue；先复核脱敏内容；
- 不要从日志中恢复 Session Token；它本来就不应被记录；
- 看 `operationId`、`status`、`attempt`、`commandFingerprint`、`error.code` 和 `recoveryInstruction`，不根据文件名顺序猜测结果。

## 6. 什么时候需要人工停下

出现以下情况时不继续自动处理：

- 任何 `do_not_retry`；
- 一个稳定身份对应多个 Figma 资产；
- 需要删除、Detach、Swap、降级或 Rebind；
- Approval 被拒绝、撤销或取代；
- 无法证明 Figma 成功后 Registry 是否已最终化；
- `INTERNAL_ERROR` 或发现可能包含凭据的日志。

上报时只提供可脱敏证据：Hatchkit 提交号、Node／pnpm 版本、重现步骤、结构化错误码、脱敏的目标逻辑 ID 和门禁输出。不提供 Token、Authorization Header、个人路径、未脱敏 Figma URL 或客户资产。
