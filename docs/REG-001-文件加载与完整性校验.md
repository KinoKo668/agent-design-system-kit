# REG-001：文件加载与完整性校验

- 状态：已实现
- 实现日期：2026-09-01
- 依赖：SCH-001 至 SCH-004、ADR-002、CORE-001、SEC-001
- 适用范围：本地设计系统目录、Registry Loader、后续 CLI 与 MCP 查询入口

## 1. 目标

REG-001 把 Git 工作区中的 JSON 设计事实转换为一个经过验证、可供 Agent 查询的内存快照。

它解决的核心问题不是“能否读到 JSON”，而是：

> Agent 读到的 Brief、Token、Component Contract 与 Registry 是否属于同一项目，身份是否唯一，引用是否准确，内容是否被改动。

任何失败都会返回机器可读的错误代码、JSON Pointer 和仓库内相对文件路径。调用方不需要猜测是哪份文件出了问题。

## 2. Package 边界

职责分为两层：

```text
mcp-server
  文件发现 · 安全读取 · JSON 解析 · SHA-256
                         │
                         ▼
core
  Schema · 项目边界 · 重复身份 · 跨资产引用 · Registry 关联
```

- `core` 保持环境无关，不读取文件，也不导入 `node:*`；
- `mcp-server` 是本地文件系统适配层；
- 后续 CLI 与 MCP Tool 应复用这条加载链路，不得另写一套宽松校验器。

## 3. 受管理目录与文件名

调用方传入设计系统根目录和准确 `projectId`。Loader 只发现以下正式目录：

| 目录          | 文件后缀          | 文档类型           |
| ------------- | ----------------- | ------------------ |
| `briefs/`     | `.brief.json`     | Design Brief       |
| `tokens/`     | `.tokens.json`    | Token Set          |
| `components/` | `.component.json` | Component Contract |
| `registry/`   | `.registry.json`  | Component Registry |

目录可以继续分层，读取顺序按相对路径稳定排序。隐藏文件和非 JSON 文件不会成为设计事实；受管理目录中后缀不正确的 JSON 会明确报错，避免把文件放错位置后被静默忽略。

`design-system/examples/` 是公开 Fixture 区，不会被正式 Loader 自动当成当前项目资产。未来示例项目应把可执行资产放进上述正式目录。

## 4. 加载流水线

一次加载按以下顺序执行：

1. 解析根目录并验证加载限制；
2. 发现四类受管理文件；
3. 拒绝软链接、非常规文件、过深目录和超量文件；
4. 限量读取并解析 JSON；
5. 按文档类型执行严格 Schema；
6. 校验所有文档的 `projectId`；
7. 校验相对来源路径、重复来源和重复资产身份；
8. 解析 Component → Token Set 引用并校验每条 Token Binding；
9. 合并多个 Registry 后检查重复 Active、版本历史和 Locator 冲突；
10. 解析 Registry → Component Contract 的准确版本与摘要；
11. 对声明了 `contentDigest` 的 Brief、Token Set 与 Component Contract 重新计算摘要。

全部通过后才返回 `DesignSystemSnapshot`。不存在“部分合法、先凑合使用”的成功结果。

## 5. 内容摘要

文件系统层使用确定性 JSON 序列化和 SHA-256：

```text
Schema 校验后的资产
→ 去掉 contentDigest 字段
→ 对象键递归排序，数组顺序保持
→ UTF-8 编码
→ SHA-256
→ sha256:<64-hex>
```

摘要使用各 Schema 已定义的显式 Digest Subject。修改名称、描述、Token 值、Variant 或 Binding 等受管理内容后，旧摘要会失效；仅改变 JSON 缩进或对象字段书写顺序不会改变摘要。

Registry 本身会把准确 Contract 摘要同时绑定到资产记录和 Figma `appliedDigest`。因此，Contract 被修改但 Registry 未更新时，加载会停止。

## 6. 错误定位合同

完整性错误保存在统一失败结果的：

```text
error.context.details.issues[]
```

每项至少包含：

```json
{
  "code": "missing_reference",
  "message": "Token Set '...' referenced by the Component Contract was not loaded.",
  "path": "/tokenSource",
  "sourcePath": "components/button.component.json"
}
```

如果问题涉及两份文件，还会返回 `relatedSourcePath`。例如 Registry 摘要与 Contract 不一致时，主路径指向 Registry，关联路径指向 Contract。

对外错误只包含设计系统根目录以内的 POSIX 相对路径，不返回本机用户名或绝对路径。操作系统错误详情也不会直接暴露。

## 7. 安全限制

默认限制为：

- 单文件最多 2 MiB；
- 最多 1000 个受管理文件；
- 最大目录深度 12；
- 文件与受管理目录均拒绝软链接；
- 打开文件时要求不跟随软链接，并在读取前后检查文件类型与字节数；
- Loader 不读取凭据文件，不写回任何文件，也不访问网络。

调用方可以收紧限制，但不能传入零、负数或非安全整数。

## 8. 公共代码入口

`@agent-design-system-kit/core` 导出：

- `validateDesignSystemSnapshot`；
- `createDesignSystemIntegrityFailure`；
- `canonicalizeJson`；
- Snapshot、来源文档与完整性问题类型。

`@agent-design-system-kit/mcp-server` 导出：

- `loadDesignSystemFromDirectory`；
- `computeJsonContentDigest`。

正式测试覆盖成功加载、确定性序列化、缺失 Token、重复身份、Registry 摘要错配、不安全来源路径、损坏 JSON、错误文件名、软链接、文件大小限制、根目录缺失与 Contract 内容篡改。

## 9. 当前不做

REG-001 不实现：

- Component 搜索、排序和唯一解析；
- Registry、Contract 或摘要的自动修复；
- Approval Record 的加载与审批状态判断；
- 文件写回、锁、事务或迁移；
- MCP 协议 Server 和 Tool；
- Figma 真实节点读取、Locator 修复或写入。

这些职责分别进入 REG-002、REG-003、MCP 与 Figma Writer 后续任务。
