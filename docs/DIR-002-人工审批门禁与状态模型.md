# DIR-002：人工审批门禁与状态模型

- 状态：冻结基线
- 决策日期：2026-08-26
- 适用范围：UI 方向、Design Token、Component Contract 与 Figma Component
- 依赖：DIR-001

## 1. 目标

本项目必须把“设计师确认过”转换成 Agent 可以读取和执行的正式状态，而不是依赖聊天记录、Figma 评论或口头约定。

审批系统需要保证：

- Agent 可以生成候选方案，但不能替代人类做最终批准；
- 每次批准都绑定准确的对象、版本和内容；
- 内容发生变化后，旧批准不能继续被误用；
- 未批准内容可以在隔离评审区预览，但不能进入正式组件库或产品页面；
- 多个 Agent 和不同会话读取到相同的批准结果；
- 所有决定可以通过 Git 历史追踪。

## 2. 三个人工审批门禁

```text
产品 Brief
→ 候选 UI 方向
→ Gate 1：UI 方向审批
→ 候选 Token
→ Gate 2：Token 审批
→ 候选 Component
→ Gate 3：Component 审批
→ 正式 Registry 与页面复用
```

后一个门禁必须引用前一个门禁的已批准版本。上游批准失效后，下游资产进入待复核状态，不得继续自动发布。

## 3. Gate 1：UI 方向审批

### 审批对象

针对同一个 Design Brief 生成的三套候选 UI 方向。

### 必需材料

- Design Brief 的 ID、版本和内容摘要；
- 三套方向的名称和设计说明；
- 颜色、字体、圆角、密度和图形语言示例；
- 每套方向至少一张可比较的关键界面或组件预览；
- Agent 对差异、优点和风险的说明；
- Figma、图片或本地评审材料链接。

### 必需批准角色

- `product_owner`：确认符合产品定位、目标用户和品牌目标；
- `design_owner`：确认视觉质量、原创性、可扩展性和设计合理性。

两种角色都批准后，系统才能将其中一个方向标记为 `approved`。同一个人可以兼任多个角色，但必须分别留下角色决策。

### 批准结果

- 同一个 Brief 版本只能有一个当前生效的 UI 方向；
- 被选方向进入 `approved`；
- 其他候选方向进入 `rejected`，但保留历史记录；
- Token 生成只能引用被批准方向的准确版本。

## 4. Gate 2：Design Token 审批

### 审批对象

基于已批准 UI 方向生成的一套 Token 版本。

### 必需材料

- 上游 UI 方向的批准记录；
- Token 文件、版本和内容摘要；
- 与上一版本的差异；
- 色彩、字体、间距、圆角和控件尺寸预览；
- Button 在 Primary、Secondary、Default 和 Disabled 下的 Token 应用预览；
- Schema 校验结果；
- 最小颜色对比度检查结果。

### 必需批准角色

- `design_owner`：确认视觉体系、语义命名和实际效果；
- `technical_owner`：确认结构可解析、引用完整、版本和迁移策略可执行。

### 批准结果

- 只有已批准 Token 才能写入正式 Figma Variables Collection；
- 候选 Token 只能写入隔离的 Review Collection 或生成静态预览；
- Component Contract 只能引用已批准 Token；
- 新 Token 版本批准后，旧版本进入 `superseded`，但不会自动删除。

## 5. Gate 3：Component 审批

### 审批对象

Component Contract、对应 Figma Component Set 及其 Variant 的组合版本。Contract 和 Figma 视觉资产不能分开批准。

### 必需材料

- 上游 Token 的批准记录；
- Component Contract 的 ID、版本和内容摘要；
- Figma Review Page 中的 Component Set；
- 所有 Variant 的完整预览；
- Contract 与 Figma 属性对照结果；
- Token 引用检查结果；
- 最小无障碍检查结果；
- 与上一版本的差异和迁移影响。

### 必需批准角色

- `design_owner`：确认视觉、状态、组件属性和使用边界；
- `technical_owner`：确认 Contract、Figma 结构、稳定身份和幂等行为。

### 批准结果

- 只有已批准组件才能登记为 Registry 中的可复用资产；
- 只有已批准组件才能进入正式 Figma Library Page；
- 页面 Agent 只能插入已批准且未被撤销或取代的组件；
- 未批准 Variant 不得由页面 Agent 临时补建。

## 6. 统一状态

所有审批对象使用同一组状态：

| 状态 | 含义 | Agent 是否可修改 | 是否可写入评审区 | 是否可进入正式库或页面 |
| --- | --- | --- | --- | --- |
| `draft` | 正在生成或编辑 | 是 | 是 | 否 |
| `in_review` | 内容已冻结，等待人工决定 | 否，需先撤回 | 是 | 否 |
| `changes_requested` | 需要修改后重新提交 | 是 | 是 | 否 |
| `approved` | 必需角色均已批准且机器校验通过 | 否，修改需新版本 | 是 | 是 |
| `rejected` | 当前版本不采用 | 否 | 仅保留历史 | 否 |
| `superseded` | 已被更新的批准版本取代 | 否 | 仅保留历史 | 不允许新增使用 |
| `revoked` | 因严重问题撤回批准 | 否 | 仅保留调查材料 | 否，已有使用需报错 |

“阻塞”“校验失败”和“Plugin 未连接”属于执行状态或错误，不得混入审批状态。

## 7. 状态转换

```text
draft
  ↓ 提交评审
in_review
  ├─→ approved
  ├─→ changes_requested ─→ draft
  └─→ rejected

approved
  ├─→ superseded
  └─→ revoked
```

转换规则：

- `draft → in_review`：提交者执行，提交后内容冻结；
- `in_review → approved`：所有必需人类角色批准，且自动校验全部通过；
- `in_review → changes_requested`：任一必需角色要求修改；
- `changes_requested → draft`：提交者开始新一轮修改；
- `in_review → rejected`：任一有否决权的必需角色明确拒绝当前版本；
- `approved → superseded`：替代它的新版本获得批准；
- `approved → revoked`：必需角色因安全、版权、品牌或严重设计问题撤回批准。

`rejected`、`superseded` 和 `revoked` 都是当前版本的终止状态。继续工作必须创建新版本，不得把终止版本直接改回 `draft`。

## 8. 批准的版本绑定

批准不是绑定文件名，而是绑定以下四项：

1. `subject.type`：方向、Token 或 Component；
2. `subject.id`：稳定逻辑 ID；
3. `subject.version`：明确版本；
4. `subject.contentDigest`：规范化内容的 SHA-256 摘要。

审批记录还应保存被评审内容所在的 Git commit。Writer 在正式写入前必须重新计算摘要，并与批准记录比较。

出现以下任一情况，批准均视为过期：

- 内容摘要不一致；
- 上游依赖版本发生变化；
- 批准记录被撤销；
- 当前对象已经被更新版本取代；
- 必需角色的批准不完整。

过期不是自动批准新内容。系统必须重新进入评审流程。

## 9. 审批记录格式

第一版使用 JSON 保存审批记录，建议路径为：

```text
design-system/approvals/
├── directions/<id>/<version>.approval.json
├── tokens/<id>/<version>.approval.json
└── components/<id>/<version>.approval.json
```

最小结构示例：

```json
{
  "schemaVersion": "1.0",
  "approvalId": "approval.component.button.1.0.0",
  "subject": {
    "type": "component",
    "id": "button",
    "version": "1.0.0",
    "contentDigest": "sha256:<digest>",
    "gitCommit": "<commit-sha>"
  },
  "dependencies": [
    {
      "type": "tokens",
      "id": "foundation",
      "version": "1.0.0",
      "approvalId": "approval.tokens.foundation.1.0.0"
    }
  ],
  "status": "approved",
  "policy": {
    "requiredRoles": ["design_owner", "technical_owner"]
  },
  "submission": {
    "submittedBy": "agent:codex",
    "submittedAt": "2026-08-26T00:00:00Z"
  },
  "decisions": [
    {
      "role": "design_owner",
      "reviewer": "github:<reviewer-id>",
      "decision": "approved",
      "decidedAt": "2026-08-26T00:00:00Z",
      "summary": "Visual review passed."
    },
    {
      "role": "technical_owner",
      "reviewer": "github:<reviewer-id>",
      "decision": "approved",
      "decidedAt": "2026-08-26T00:00:00Z",
      "summary": "Contract and Figma structure checks passed."
    }
  ],
  "validations": [
    {
      "check": "schema",
      "status": "passed",
      "evidence": "artifacts://validation/schema.json"
    }
  ],
  "evidence": [
    {
      "kind": "figma",
      "uri": "<figma-review-url>"
    }
  ],
  "supersedes": null
}
```

最终 JSON Schema 由后续 Schema 任务实现；DIR-002 冻结字段语义和行为，不冻结具体代码库。

## 10. 决策规则

- `submittedBy` 可以是 Agent 或人；
- `reviewer` 必须代表真实人类身份；
- Agent 不得写入代表人类的批准决定；
- 自动校验只能提供证据，不能代替人类批准；
- 任一必需角色给出 `rejected`，当前版本即被拒绝；
- 任一必需角色给出 `changes_requested`，对象必须返回修改状态；
- 所有必需角色批准且所有 P0 校验通过，派生状态才是 `approved`；
- `status` 必须能够由决策和校验结果重新计算，不能只信任文件中的单个字符串。

## 11. Figma 写入边界

Figma Writer 每次写入前必须重新读取审批记录和内容摘要。

### 允许的预览写入

`draft`、`in_review` 和 `changes_requested` 可以写入专用 Review Page 或 Review Variables Collection，用于设计师评审。

预览资产必须：

- 与正式 Library Page 隔离；
- 带有 Draft 或 Review 标记；
- 不登记为页面 Agent 可用资产；
- 不允许被产品页面查询和插入。

### 允许的正式写入

只有 `approved` 且内容摘要匹配的对象可以：

- 写入正式 Variables Collection；
- 写入或更新正式 Component Library Page；
- 在 Registry 中标记为可用；
- 被页面 Agent 解析和插入。

### 旧版本处理

- `superseded`：已有 Instance 保留并产生升级提示，不允许新插入；
- `revoked`：禁止新插入，审计现有 Instance 时产生错误；
- 系统不得自动删除旧 Component 或批量替换 Instance。

## 12. 标准错误代码

| 错误代码 | 触发条件 | Agent 下一步 |
| --- | --- | --- |
| `APPROVAL_REQUIRED` | 没有审批记录 | 提交人工评审 |
| `APPROVAL_IN_REVIEW` | 正在等待决定 | 等待人类审批 |
| `APPROVAL_CHANGES_REQUESTED` | 评审要求修改 | 根据意见创建修改版本 |
| `APPROVAL_INCOMPLETE` | 缺少必需角色决定 | 提醒对应负责人审批 |
| `APPROVAL_REJECTED` | 当前版本被拒绝 | 创建新版本，不得写入 |
| `APPROVAL_STALE` | 摘要或依赖版本不匹配 | 重新提交当前内容评审 |
| `APPROVAL_SUPERSEDED` | 已有更新批准版本 | 改用新版本 |
| `APPROVAL_REVOKED` | 批准已被撤回 | 停止使用并报告现有影响 |
| `VALIDATION_FAILED` | 自动 P0 校验失败 | 修复校验问题后重新提交 |

错误结果必须包含审批对象、当前状态、缺失条件和建议下一步，不能只返回“无权限”或“失败”。

## 13. 数据事实源

- GitHub 中的审批 JSON 是机器事实源；
- Git 历史提供决定变更记录；
- Figma 评论、聊天记录和会议结论只能作为证据链接；
- Figma 节点名称或页面位置不能代替批准记录；
- Registry 必须引用审批 ID，而不是保存一个无法追踪来源的 `approved: true`。

## 14. DIR-002 完成标准

- 三个审批门禁的对象、材料、角色和结果明确；
- 统一状态及合法转换明确；
- 批准与版本、内容摘要和上游依赖绑定；
- 审批记录最小字段明确；
- Review 与正式 Figma 写入边界明确；
- Agent、人工 Reviewer 和 Writer 权限明确；
- 错误代码及恢复动作明确；
- 后续 Schema、MCP 和 Figma Writer 可以直接引用本基线。
