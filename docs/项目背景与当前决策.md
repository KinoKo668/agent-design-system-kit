## 项目起点

本项目希望为 ChatGPT、Codex、Claude、Cursor、Antigravity 等 Agent 提供更完整的前端 UI 设计能力，重点服务需要从零建立 Figma Components 和整体视觉语言的新项目。

主要问题是：不同会话、不同 Agent 或多人协作时，设计上下文容易丢失，导致颜色、按钮、图标、间距和组件逐渐不统一。

## 产品目标

将专业 UI 设计师在新项目开始阶段的工作方法，转化为 Agent 可以执行、检查和恢复的流程。

最终希望实现：

- 从产品定位产生多个可评审的 UI 方向；
- 人工确认方向后建立 Token 和 Figma Components；
- 用机器可读的 Component Contract 记录组件规则；
- 用 Registry 记录 Contract、Figma Component 和代码组件之间的关系；
- 后续 Agent 设计页面时优先使用已经批准的组件；
- 通过自动审计防止硬编码样式和设计漂移。

## 已确认的概念关系

```text
Token → Component → Instance → 页面设计稿
```

- Token 是颜色、间距、字号和圆角等被命名的设计决定。
- Component 是使用 Token 建立的可复用 UI 元素。
- Instance 是放入某个页面的 Component 副本。
- Agent 不通过 Token 直接寻找 Button，而是先查询 Button Contract 和 Registry。
- Registry 提供准确的 Figma Component Key，Agent 再插入真实 Instance。

## 建议的源码开放形态

项目采用本地优先架构：

```text
Agent
  ↓
本地 MCP Server
  ↓
设计系统项目文件
  ↓
Figma Plugin 或 Figma MCP
  ↓
Figma 文件
```

项目本身不托管 AI 模型，不承担模型调用费用。用户使用自己的 Codex、Claude 或其他 Agent。

第一版不需要云服务器、数据库、账号系统或管理后台。

## 市场判断

现有产品分别覆盖部分能力：

- Figma Agent 和 Figma MCP 负责操作画布及读取设计系统；
- Tokens Studio 负责 Token 管理与同步；
- Supernova、Onefold 负责设计系统上下文和治理；
- Mimic AI、Layout 等公开源码项目负责让 Agent 使用既有组件。

项目的差异化重点应放在：

1. 面向新项目从零完成 UI 定调；
2. 将设计师判断转化为可执行流程；
3. 建立跨 Agent 的组件契约和治理机制；
4. 将 Figma 建库与后续页面复用连接成闭环。

## 下一步建议

先完成一条最小垂直链路，而不是一次建设完整平台：

1. 定义 Design Brief Schema；
2. 定义 Token Schema；
3. 定义 Button Component Contract；
4. 建立最小 Registry；
5. 通过本地 MCP 查询 Button；
6. 在 Figma 中插入真实 Button Instance；
7. 检查重复执行是否会产生重复组件；
8. 检查页面是否存在硬编码样式。

该链路的冻结范围、输入输出、失败路径和不做事项参见 [DIR-001：Button 垂直验证链路](DIR-001-Button垂直验证链路.md)。
