# GOV-001：审批记录与写前校验

## 1. 结论

Hatch 现在具备可机器读取的 Approval Record、审批状态推导、Git 目录加载和 Figma 写前实时校验能力。

Bridge 不相信命令里声称“已经批准”的文字。每次正式写命令进入队列前，它都会重新读取本地 Git 工作树中的设计资产与 Approval Record，校验准确项目、资产、版本、内容摘要、人工角色、自动检查和完整上游审批链。任一条件变化，写入立即停止。

这项能力不会创建或伪造人工决定。当前公开 `hatch-demo` 仍没有真实 Approval Record，因此即使以校验模式启动 Bridge，正式 Figma 写入仍会被正确阻断。

## 2. Approval Record 保存位置

```text
design-system/<project-id>/approvals/
├── directions/<asset-id>/<version>.approval.json
├── tokens/<asset-id>/<version>.approval.json
└── components/<asset-id>/<version>.approval.json
```

每份记录使用确定性 ID：

```text
approval.direction.<asset-id>.<version>
approval.tokens.<asset-id>.<version>
approval.component.<asset-id>.<version>
```

审批对象同时绑定 `projectId + type + assetId + assetVersion + contentDigest + gitCommit`。内容或版本变化后，旧记录不能继续授权新内容。

## 3. 状态不由文件作者决定

记录中的 `status` 必须与证据推导结果一致：

- 未提交为 `draft`；
- 已提交但条件不全为 `in_review`；
- 有 `changes_requested` 或 `rejected` 决定时进入对应状态；
- 所有必需人工角色批准、所有必需 P0 检查通过且存在证据时，才是 `approved`；
- 只有曾经完整批准的记录才能被 `revoked` 或 `superseded`。

Reviewer 必须使用 `github:` 或 `human:` 身份。`agent:` 可以提交材料，但不能填入人工审批字段。当前本地 Schema 能验证身份命名和 Git 中的记录内容，但不能仅凭一个字符串认证此人确实控制对应 GitHub 账号；首版的身份真实性仍依赖受保护分支、CODEOWNERS／PR Review 和仓库审计历史，不能把未经 Review 的本地 JSON 当作可信人工决定。

## 4. 固定审批策略

| 对象         | 必需人工角色                  | 必需 P0 检查                                                   | 唯一上游类型 |
| ------------ | ----------------------------- | -------------------------------------------------------------- | ------------ |
| UI Direction | Product Owner、Design Owner   | Schema、Visual Review                                          | Design Brief |
| Token Set    | Design Owner、Technical Owner | Schema、Token References、Color Contrast                       | UI Direction |
| Component    | Design Owner、Technical Owner | Schema、Contract/Figma Parity、Token References、Accessibility | Token Set    |

Token 或 Component 即使自身仍为 `approved`，只要上游方向或 Token 被撤销、取代、缺失或摘要不匹配，下游写入也会返回 `APPROVAL_STALE`。

## 5. Git Loader 完整性检查

CLI 的 `--approval` 来源和 MCP Server 的 `approvals/**/*.approval.json` 自动发现都会执行同一套 Core 校验：

- 拒绝重复 Approval ID；
- 验证 Token／Component 审批摘要与当前源文件一致；
- 验证 Brief 依赖摘要；
- 验证依赖记录的准确 Subject；
- 验证 `supersedes` 只能指向同一逻辑资产的更早 SemVer；
- 验证替代记录必须是同一逻辑资产的更晚 SemVer，并双向关联；
- 保留 revoked／superseded 历史记录，但不允许其授权写入。

UI Direction Schema 尚未实现，因此当前只能验证 Direction 的 Approval 结构与 Brief 依赖，暂不能把 Direction Subject 摘要反查到正式 Direction 源文件。该缺口属于 LOOP-004。

## 6. Bridge 启动模式

仅诊断模式允许 `writer.ping`，拒绝所有 Figma 写入：

```bash
pnpm build
pnpm hatchkit:figma-bridge
```

Git Approval 校验模式：

```bash
pnpm hatchkit:figma-bridge -- --project hatch-demo --root design-system/hatch-demo
```

也可以使用 `HATCHKIT_PROJECT_ID` 与 `HATCHKIT_DESIGN_SYSTEM_ROOT`。项目与 Root 必须同时提供；部分配置、重复参数和未知参数会在启动时失败。

启用校验器只表示 Bridge 会检查审批，不表示资产已经获得批准。只有准确的真实人工 Approval Record 完整存在时，匹配的写命令才会进入单 Writer 队列。

## 7. 失败安全边界

- 每条写命令都重新读取磁盘，不使用进程启动时的审批缓存；
- Loader 失败、项目不匹配、重复身份、过期摘要、撤销或取代都会阻断；
- `writer.ping` 不修改 Figma，因此不需要资产审批；
- 任何 Prompt、Agent 输出或临时技术标记都不能替代 Approval Record；
- `github:`／`human:` 前缀不是密码学签名，未经仓库 Review 的本地记录不构成可信批准；
- 不提供跳过人工审批的开发后门。

## 8. 当前验证与下一步

自动测试已覆盖批准、缺少角色、拒绝、撤销、上游失效、重复 ID、摘要漂移、错误版本谱系、每次命令重新读取和 Loader 故障。

下一步由真实 Product／Design／Technical Owner 对明确版本留下真实决定和证据，再在用户指定的独立 Figma 文件中完成 FIG-003 两次相同 Ensure。没有这些前置条件时，保持写入关闭是正确结果。
