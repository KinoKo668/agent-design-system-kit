# SEC-001：本地凭据与日志脱敏策略

- 状态：已实现
- 实现日期：2026-08-31
- 依赖：ENG-002、CORE-001、SPIKE-002
- 适用范围：本地 MCP Server、Figma Plugin、CLI、Git 仓库与 GitHub Actions

## 1. 目标

Hatch 第一版不自建云服务器，也不建立账号系统。本策略解决三个问题：

1. 本地 MCP Server 与 Figma Plugin 如何安全确认彼此属于同一次会话；
2. 将来需要调用 Figma REST API 时，凭据从哪里来、保存在哪里；
3. 即使调用方误把敏感内容放进日志字段，正式日志模型也尽量不泄露。

安全边界是“失败时停止”，而不是“凭据有问题时继续尝试写 Figma”。缺失、无效、过期或来自不安全来源的凭据必须在写入前阻断。

## 2. 第一版到底需要哪些凭据

### 2.1 Figma Plugin 写入：不需要 PAT

Plugin 在用户已经登录的 Figma Desktop 中运行，并通过 Figma Plugin API 修改当前文件。第一版正式 Writer 走这条链路，因此不需要把 Figma Personal Access Token 交给 Plugin。

### 2.2 本地 Bridge：需要短期 Session Token

本地 MCP Server 与 Plugin 通过仅监听 `127.0.0.1` 的 Bridge 通信。MCP Server 启动时使用密码学安全随机源生成一次性 Session Token：

- 只存在于 MCP Server 与当前 Plugin UI 的进程内存；
- 不写入 Git、配置文件、日志、URL、命令行参数或 Figma 节点；
- Server 重启、Plugin 断开或会话超时后失效；
- 每次请求通过 Authorization Header 携带，并在进入业务队列前验证；
- 不正确的 Token 只能返回安全错误，不能进入 Writer 队列。

具体随机数生成、有效期和常量时间比较在 FIG-002 实现。SEC-001 先冻结数据边界与错误合同。

### 2.3 可选 Figma REST：以后才需要 PAT

只有未来增加 Figma REST 只读诊断或资产同步时，才允许使用个人访问令牌。Figma 说明 PAT 代表用户权限，应按单一集成创建、配置最小 Scope 和过期时间，并可随时撤销。Hatch 约定可选环境变量名为 `HATCH_FIGMA_ACCESS_TOKEN`，但第一版不会自动读取 `.env` 文件，也不会要求用户创建 PAT。

正式对外分发若需要代表其他用户调用 REST API，必须单独设计 OAuth；不得把个人 PAT 当作多人共享凭据。

## 3. 允许与禁止的保存位置

| 位置 | Bridge Session Token | Figma PAT | 说明 |
| --- | --- | --- | --- |
| 进程内存 | 允许 | 允许 | 运行期间的唯一通用保存位置 |
| 操作系统钥匙串 | 不需要 | 未来允许 | 由平台 Adapter 实现，不放进 `core` |
| 进程环境变量 | 禁止 | 未来允许 | 只允许 `HATCH_FIGMA_ACCESS_TOKEN`，不得打印环境 |
| `.env` / 本地凭据文件 | 默认禁止 | 默认禁止 | 仓库已忽略，但第一版不自动加载 |
| CLI 参数、URL Query | 禁止 | 禁止 | 容易进入 Shell 历史、进程列表或访问日志 |
| Git / GitHub Issue / PR | 禁止 | 禁止 | 包括示例、Fixture、截图与报错内容 |
| Figma Shared Plugin Data | 禁止 | 禁止 | 任何其他 Plugin 都可能读取 |
| Figma Plugin Data | 禁止 | 禁止 | 不作为密钥保险箱 |
| Figma `clientStorage` | 禁止持久化 | 禁止持久化 | Figma 明确说明其隐私目标不等于安全保险箱 |
| 日志、Telemetry、Crash Report | 禁止 | 禁止 | 只能记录凭据类别和安全错误码 |

Figma 的 [clientStorage 文档](https://developers.figma.com/docs/plugins/api/figma-clientStorage/) 明确说明其设计目标是稳定性与隐私而非安全，用户仍可检查数据；[Shared Plugin Data 文档](https://developers.figma.com/docs/plugins/api/properties/nodes-setsharedplugindata/) 说明其他 Plugin 可以读取共享数据。因此两者都不能承载凭据。

## 4. 仓库防护

`.gitignore` 覆盖以下本地内容：

- `.env` 与变体；
- `.secrets/`；
- 常见私钥与证书文件；
- `credentials.local.json`；
- Hatch 本地运行状态与日志目录。

忽略规则只是减少误提交，不是密钥管理系统。任何示例只能使用明显的假值，不能复制真实 Token 的片段。提交前必须检查暂存区；公开仓库可把 GitHub Secret Scanning 与 Push Protection 作为额外防线。GitHub 也提醒自动遮盖不是绝对保证，变形后的或结构化的 Secret 可能不会被识别，因此不能依赖 CI 日志平台替代应用层脱敏。参见 [Secret scanning scope](https://docs.github.com/en/code-security/reference/secret-security/secret-scanning-scope)、[Push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection) 与 [Secure use of GitHub Actions](https://docs.github.com/en/actions/reference/security/secure-use)。

## 5. GitHub Actions 边界

当前 `Quality` Workflow：

- 不声明也不读取任何项目 Secret；
- 只使用 `pull_request`，不使用高风险的 `pull_request_target`；
- 默认权限为 `contents: read`；
- Checkout 不保留 Git 凭据；
- 第三方 Action 使用完整 Commit SHA 固定版本；
- 测试必须用虚构凭据。

未来若某项验证需要真实 Figma 凭据，应放到人工触发、受保护环境的独立 Workflow，不能让来自 Fork 的代码接触凭据。GitHub 对 `pull_request_target` 和不可信代码执行风险的说明见 [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use#preventing-pwn-requests)。

## 6. 日志脱敏合同

`@agent-design-system-kit/core` 现在提供纯函数脱敏层：

- `redactSensitiveText`：遮盖调用方提供的精确运行时密钥；
- `redactJsonObject` / `redactJsonValue`：递归遮盖敏感字段；
- `isSensitiveFieldName`：识别 Authorization、Access Token、Session Token、Figma File Key、Figma Node ID、Cookie、Password 等字段；
- `createLogEvent`：在创建日志事件时强制调用上述脱敏，并要求调用方显式提供 `sensitiveValues`。

自动识别内容包括：

- Bearer 与 `X-Figma-Token` Header；
- 以 `TOKEN`、`SECRET`、`PASSWORD`、`API_KEY` 等结尾的环境变量赋值；
- Figma 文件 URL；
- macOS、Linux 与 Windows 个人目录路径；
- 嵌套 JSON 中的敏感字段和值。

`sensitiveValues` 只参与创建过程，不会出现在最终 `LogEvent`。设计系统中的 `designTokenId` 不属于安全凭据，不会因为名称中含有 Token 而被误删。

调用方仍负有两项责任：

1. 把当前内存中的真实 Secret 传给 `sensitiveValues`；
2. 不把原始异常对象、Stack、Request Header 或整个环境变量对象塞进日志。

## 7. 安全错误与失败方式

SEC-001 增加四个稳定错误码：

| 错误码 | 触发条件 | 行为 |
| --- | --- | --- |
| `CREDENTIAL_REQUIRED` | 必需凭据未提供 | 写入前停止，提示通过安全入口提供 |
| `CREDENTIAL_INVALID` | 格式或验证结果不合法 | 停止，替换凭据后重新请求 |
| `CREDENTIAL_EXPIRED` | 凭据过期或会话已失效 | 停止，轮换或重连后重试 |
| `UNSAFE_CREDENTIAL_SOURCE` | 凭据来自参数、仓库文件等禁止位置 | 不重试，先迁移到安全来源 |

错误的 `message`、`context` 与恢复指令只能描述凭据的种类、来源类别和状态，不能回显值、前后缀、Header 或个人 Figma 定位信息。

## 8. 泄漏后的处理

一旦怀疑凭据泄漏：

1. 立即停止相关 Writer 与 Bridge 会话；
2. 在 Figma 撤销或轮换 PAT；Session Token 通过重启本地 Server 失效；
3. 检查 Git 历史、Actions 日志、Issue、PR、截图与本地日志；
4. 删除公开内容不等于凭据恢复安全，必须先撤销凭据；
5. 记录事件原因并补测试，避免相同输入再次进入日志。

Figma PAT 的创建、Scope、过期与撤销行为参见 [Figma Personal access tokens](https://developers.figma.com/docs/rest-api/personal-access-tokens/) 和 [Figma authentication](https://developers.figma.com/docs/rest-api/authentication/)。

## 9. 当前不做

SEC-001 不实现：

- 操作系统钥匙串 Adapter；
- OAuth 登录与 Refresh Token 生命周期；
- 云端 Secret Manager；
- CI 中访问真实 Figma 文件；
- 网络监听、Session Token 生成与校验的正式 Bridge；
- 自动清理已经进入第三方平台的历史 Secret。

这些能力只有在对应产品链路需要时再实现，不为第一版引入服务器和持续运营成本。

## 10. 完成标准

- 第一版所需与不需要的凭据已经明确；
- Git、Figma、日志与运行时存储边界已经冻结；
- 四个安全错误从 `core` 公共入口导出；
- Log Event 默认经过字段、模式、路径、Figma URL 与精确值脱敏；
- 脱敏不会修改原始输入，也不会误伤 `designTokenId`；
- GitHub Actions 无 Secret、最小权限且不执行 `pull_request_target`；
- Node 24 与 Node 22 的统一质量门禁通过。
